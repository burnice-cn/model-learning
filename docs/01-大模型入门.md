# 01. 大模型入门：先建立正确的底层图景

## 1. 深度学习模型到底在存什么？

一个模型文件里主要存的是**参数**。参数通常是浮点数矩阵、向量或高阶张量：

```text
权重文件 = 大量 Tensor + 每个 Tensor 的名字、形状、dtype、数据偏移
```

例如：

```text
layers.0.attn.q_proj.weight
shape = [4096, 4096]
dtype = bfloat16
元素数 = 16,777,216
字节 = 33,554,432
```

模型越大，参数越多。参数量常用单位：

| 单位 | 数量 |
|---|---:|
| K | 10^3 |
| M | 10^6 |
| B | 10^9，中文常称“十亿参数” |

参数量本身不直接等于智能水平，但它决定了几件硬事实：

- 加载需要多少内存；
- 一次前向需要多少乘加计算；
- 磁盘上需要多大空间；
- 什么硬件能跑，什么硬件根本放不下。

## 2. 模型目录里的文件类型

一个“模型”通常不是一个单独文件，而是一个目录。目录里既有**结构配置**，也有**权重数据**，还有 tokenizer 和调度器需要的配置。

可以把文件分成四类：

```text
1. 管线清单：说明这个目录要组装成什么 Pipeline，包含哪些组件
2. 结构配置：说明每个网络有多深、多宽、用什么算子
3. 权重数据：真正的大文件，保存训练好的参数
4. 辅助配置：tokenizer、scheduler、图像预处理等
```

### 2.1 `model_index.json`：管线装配清单

这是 diffusers 管线目录的入口文件。它回答的问题是：

```text
这个目录应该创建什么 Pipeline？
这个 Pipeline 由哪些组件组成？
每个组件用什么类加载？
```

例如 Qwen-Image-2512：

```json
{
  "_class_name": "QwenImagePipeline",
  "scheduler": ["diffusers", "FlowMatchEulerDiscreteScheduler"],
  "text_encoder": ["transformers", "Qwen2_5_VLForConditionalGeneration"],
  "tokenizer": ["transformers", "Qwen2Tokenizer"],
  "transformer": ["diffusers", "QwenImageTransformer2DModel"],
  "vae": ["diffusers", "AutoencoderKLQwenImage"]
}
```

`model_index.json` 不保存权重，也不定义网络内部细节；它只告诉加载器“要找哪些子目录、创建哪些对象、最后怎么组装”。

### 2.2 `config.json`：组件结构图

每个网络组件都有自己的 `config.json`。例如 `transformer/config.json` 里有：

```json
{
  "num_layers": 60,
  "num_attention_heads": 24,
  "attention_head_dim": 128,
  "in_channels": 64,
  "out_channels": 16
}
```

它告诉框架：

- 建多少层；
- 每层有多少注意力头；
- 输入输出通道是多少；
- 用什么激活函数、归一化方式；
- 参数的形状应该怎么创建。

换句话说：

```text
config.json 决定“骨架”
权重文件决定“肌肉和记忆”
```

同一个模型如果只有 `config.json`，通常只能随机初始化，不能复现训练好的输出。

### 2.3 `*.safetensors`：权重文件

`*.safetensors` 是当前推荐的大模型权重格式。它保存真实参数，例如：

```text
layers.0.attn.q_proj.weight
layers.0.attn.k_proj.weight
layers.0.attn.v_proj.weight
```

safetensors 文件内部大致是：

```text
[8 字节 header 长度][JSON header][连续的 tensor 数据区]
```

JSON header 记录每个参数的：

- 名字；
- dtype；
- shape；
- 数据在文件中的 offset。

因此它可以支持随机访问某个张量，而不必先读取整个文件。这也是本项目 Qwen 磁盘流式加载的基础。

### 2.4 `*.bin`：旧式 PyTorch 权重

老项目里可能看到：

```text
pytorch_model.bin
diffusion_pytorch_model.bin
```

这通常是 `torch.save()` 保存的 PyTorch checkpoint。缺点是：

- 常依赖 pickle；
- 加载不可信文件时有安全风险；
- 随机访问和流式加载不如 safetensors 方便。

现在更推荐使用 safetensors。本仓库模型主要使用 `.safetensors`。

### 2.5 分片权重和 `*.index.json`

大模型经常不能塞进一个文件，于是按大小拆成多个 shard：

```text
model-00001-of-00004.safetensors
model-00002-of-00004.safetensors
model-00003-of-00004.safetensors
model-00004-of-00004.safetensors
model.safetensors.index.json
```

例如 Qwen-Image-2512 的：

```text
transformer/
├── diffusion_pytorch_model-00001-of-00009.safetensors
├── ...
├── diffusion_pytorch_model-00009-of-00009.safetensors
└── diffusion_pytorch_model.safetensors.index.json
```

`*.index.json` 里的 `weight_map` 会记录：

```text
参数名 → 所在 shard 文件
```

加载器先读 index，再打开对应分片取参数。缺少 index 或任何一个 shard 都会导致加载失败。

### 2.6 fp16 / fp32 / variant 文件名

同一个组件可能有不同 dtype 版本：

```text
model.safetensors
model.fp16.safetensors
model.fp32.safetensors
```

在 diffusers 中，`variant="fp16"` 表示选择文件名带 `.fp16` 的那套权重：

```python
StableDiffusionPipeline.from_pretrained(
    model_path,
    variant="fp16",
    dtype=torch.float32,
)
```

注意两个概念不同：

| 概念 | 含义 |
|---|---|
| `variant="fp16"` | 磁盘上选择哪套文件名 |
| `dtype=torch.float32` | 加载到运行时后用什么 dtype 计算 |

本仓库 SD1.5 目录里还存在软链接：

```text
model.safetensors -> model.fp16.safetensors
```

软链接不会额外复制一份权重，只是提供另一个可访问的文件名。

### 2.7 Tokenizer 文件

常见文件包括：

| 文件 | 作用 |
|---|---|
| `tokenizer_config.json` | tokenizer 基础配置、特殊 token、模型路径信息 |
| `special_tokens_map.json` | BOS、EOS、PAD、UNK 等特殊 token 的映射 |
| `vocab.json` | 子词或 token 到 id 的字典 |
| `merges.txt` | BPE 合并规则 |
| `tokenizer.json` | 部分库使用的已编译 tokenizer 数据 |
| `added_tokens.json` | 额外加入词表的 token |
| `chat_template.jinja` | 聊天模型的对话模板 |

这些文件通常很小，但非常重要。如果 tokenizer 和模型权重不匹配，即使权重完整，输入语义也会错。

### 2.8 Scheduler 配置

```text
scheduler/scheduler_config.json
```

它不是网络权重，而是推理“去噪计划”的配置，例如：

- 训练时间步数量；
- beta schedule；
- 是否跳过某些步骤；
- flow matching 的动态 shift 参数。

Stable Diffusion v1.5 使用 `PNDMScheduler`，Qwen-Image-2512 使用 `FlowMatchEulerDiscreteScheduler`。

### 2.9 图像预处理和生成配置

还可能看到：

| 文件 | 作用 |
|---|---|
| `preprocessor_config.json` | 图像缩放、归一化、裁剪等预处理规则 |
| `feature_extractor/config.json` | 图像特征提取配置 |
| `generation_config.json` | 文本生成模型的采样、温度、特殊 token 等配置 |

这些文件描述“输入输出怎么处理”，通常不保存大权重。

### 2.11 缓存和下载状态文件

在本地模型目录或 Hugging Face cache 中还可能看到：

```text
*.lock
*.metadata
.cache/
```

这些是下载工具的锁文件、断点续传元数据或缓存目录，通常不是模型权重。加载失败时不要只看文件名存在，还要确认分片大小和 index 引用是否完整。

如果你还想继续深入 `model_index.json`、`from_pretrained`、variant 和分片加载的执行流程，请看 [03-diffusers管线与模型加载.md](03-diffusers管线与模型加载.md)。

## 3. 推理和训练的区别

### 训练

训练是“学参数”：

```text
输入 → 模型输出 → 与答案比较 → 计算梯度 → 更新参数
```

训练需要反复读写参数和中间激活值，通常比推理耗资源多一个数量级。

### 推理

推理是“用已经学好的参数做预测”：

```text
输入 → 前向计算 → 输出
```

本项目只做推理。脚本里的这一行就是关闭梯度，表明不训练：

```python
torch.set_grad_enabled(False)
```

推理只需要前向计算，但模型参数仍然必须参与计算。

## 4. Token：神经网络看到的不是文字

神经网络的核心运算只认识数字张量。文本必须先转换成整数序列：

```text
"a cat astronaut"
→ tokenizer
→ [64, 2368, 763, 1131, 380, 4722]
```

这些整数叫 **token id**。每个 token id 再通过 embedding 表变成向量：

```text
token id 2368
→ 查 embedding 矩阵的第 2368 行
→ 一个 768 维或 3584 维向量
```

这一步之后，模型才能处理“含义”。详细机制见 [02-Tokenizer与文本编码.md](02-Tokenizer与文本编码.md)。

## 5. Transformer：把上下文变成表示

Transformer 的核心思想是：**每个 token 的表示都可以参考其他相关 token 的表示**。

一个简化流程：

```text
token embeddings
  → self-attention：判断谁和谁相关
  → feed-forward MLP：对每个位置做非线性变换
  → residual + normalization
  → 重复 N 层
  → 输出表示
```

### Self-attention 直觉

对一句话：

```text
The cat sits on the mat because it is tired.
```

模型需要知道 `it` 很可能指 `cat`。self-attention 允许 `it` 这个位置去查询序列中的其他位置，并根据相关性加权汇总信息。

每个 attention 层会学习三类投影：

| 名称 | 作用 |
|---|---|
| Query | 我要找什么？ |
| Key | 我能提供什么索引？ |
| Value | 如果你选中我，我给你什么内容？ |

再通俗一点：

```text
Q：我要找“主语是谁”
K：我是 cat / sits / mat / tired ...
V：cat 的语义向量、mat 的语义向量 ...
attention(Q,K) → 相关性分数
按分数加权 V → it 的上下文表示
```

### 多头注意力

一个 attention head 只能学一种关系。多头注意力让不同的 head 学不同模式：

- 一个 head 关注语法关系；
- 一个 head 关注指代关系；
- 一个 head 关注局部相邻词；
- 一个 head 关注长距离依赖。

## 6. 自回归 LLM 和扩散模型的不同

### 自回归 LLM

ChatGPT、Qwen、LLaMA 这类文本生成模型通常按顺序生成：

```text
输入 prompt tokens
→ 预测下一个 token
→ append 到序列
→ 再预测下一个 token
→ 循环
```

它像“一个字一个字往下写”。

### 扩散模型

Stable Diffusion 和 Qwen-Image 是图像生成模型。它们不逐像素地写图像，而是从随机噪声开始，反复“去噪”：

```text
随机 latent 噪声 x_T
→ step 1 预测噪声并去掉一点
→ step 2 再去掉一点
→ ...
→ x_0 接近干净 latent
→ VAE 解码成 RGB 图片
```

它像“先有一团噪声，再把结构逐渐显影出来”。

### 文本如何控制图像？

文本先被 text encoder 变成向量，然后在图像生成网络中通过 cross-attention / joint attention 参与：

```text
"a cat astronaut"
→ text encoder
→ 语义向量
→ 去噪网络根据这些向量决定：画猫、画宇航服、画太空背景
```

## 7. 为什么要看参数量和 dtype？

模型内存的粗略计算：

```text
权重字节数 ≈ 参数量 × 每个 dtype 的字节数
```

| dtype | 每参数字节 | 常见用途 |
|---|---:|---|
| fp32 / float32 | 4 | 训练常用，CPU 兼容性最好 |
| fp16 / half | 2 | GPU 推理常用 |
| bf16 / bfloat16 | 2 | 数值范围大，现代大模型常用 |
| int8 | 1 | 量化推理 |
| int4 | 0.5 | 极限压缩，但精度和兼容性要验证 |

举例：

```text
20B 参数，bf16：
20 × 10^9 × 2 = 40 GB 权重
```

这还只是权重。推理还需要额外空间：

- 激活值；
- attention 中间矩阵；
- KV cache（文本自回归模型）；
- 输入输出缓冲；
- PyTorch/驱动/操作系统的额外开销。

所以经验上至少要给模型权重之外留 20% 以上余量，注意力长序列时余量更大。

## 8. 计算量：为什么参数大不只意味着内存大

一次大矩阵乘法大致需要：

```text
FLOPs ≈ 2 × 输入元素数 × 权重参数量
```

也就是说，**参数参与计算时，算力和内存带宽都会成为瓶颈**。

- GPU 擅长大规模并行矩阵乘法；
- CPU 也能做，但吞吐低很多；
- 如果权重在磁盘上，还需要考虑 I/O；
- 如果内存不足，系统进入 swap，性能可能断崖式下降。

本机是 i5-14400 CPU，没有 NVIDIA GPU。Stable Diffusion v1.5 在 CPU 上可以接受；Qwen-Image-2512 在 CPU 上可以“研究可行性”，但速度很慢。

## 9. 稀疏 MoE 与普通 dense 模型

有些新模型采用 MoE（Mixture of Experts）：

- 总参数很大；
- 每个 token 只激活一部分专家；
- 磁盘占用由总参数决定；
- 每步计算量由激活参数决定。

因此要区分：

```text
总参数量 ≠ 每次激活参数量
```

Qwen-Image-2512 的核心生成网络并不是典型 MoE 文本模型；本仓库讨论的重点仍是加载与推理，而不是 MoE 路由。

## 10. 本项目里两类“模型”的层次

不要把 `models/xxx/` 目录理解成一个单文件模型。diffusers 管线通常由多个组件组成：

### Stable Diffusion v1.5

| 组件 | 作用 |
|---|---|
| tokenizer | 文本切 token |
| text_encoder | CLIP 文本编码器，输出语义向量 |
| unet | 去噪网络 |
| vae | latent ↔ RGB 图像 |
| scheduler | 去噪时间表和更新公式 |
| safety_checker | 安全检查器，本项目加载时禁用 |

### Qwen-Image-2512

| 组件 | 作用 |
|---|---|
| tokenizer | Qwen BPE tokenizer |
| text_encoder | Qwen2.5-VL 编码器 |
| transformer | 去噪网络 |
| vae | latent ↔ RGB 图像 |
| scheduler | Flow Match Euler 调度 |
