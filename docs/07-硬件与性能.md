# 07. 硬件与性能

> 记录日期：2026-09-16  
> 环境：Windows + WSL2 Ubuntu 24.04.3，项目目录位于 WSL ext4 文件系统内。

## 1. 系统概览

| 项目 | 当前值 |
|---|---|
| 操作系统 | Ubuntu 24.04.3 LTS |
| 内核 | 6.18.33.2-microsoft-standard-WSL2 |
| 主机环境 | Windows + WSL2 |
| CPU | Intel Core i5-14400 |
| 逻辑线程 | 16 |
| WSL 内存上限 | 19 GiB |
| Swap | 8 GiB |
| 可用 NVIDIA GPU | 无 |

WSL2 不是裸金属 Linux：

- `/` 是虚拟磁盘；
- I/O 行为与真实 Linux 磁盘不完全相同；
- 内存实际来自 Windows 宿主机；
- 如果进入 swap，推理速度可能极差。

### 指令集

| 指令集 | 支持 | 意义 |
|---|---|---|
| AVX2 | 支持 | 256 位向量计算 |
| FMA | 支持 | 融合乘加，有助矩阵乘法 |

结论：这台 CPU 有基础的 AVX2/FMA 推理能力，也有 int8 优化潜力，但没有 AVX-512/AMX，不能期望达到高端推理服务器的吞吐。

## 4. 存储

### 4.1 WSL 与 Windows 磁盘

当前观察：

```text
/         可用显示约 775 GiB
C:        可用约 33 GiB
D:        可用约 165 GiB
```

`df -h /` 显示的是 WSL 虚拟文件系统的可用空间，不能简单等同于 Windows 宿主盘的长期可用空间。WSL 的 VHDX 实际由 Windows 物理盘支撑，继续写入最终仍受宿主盘限制。

### 4.2 模型占用

```text
models/stable-diffusion-v1-5  约 2.0 GB
models/Qwen-Image-2512        约 54 GB
```

### 4.3 `/mnt/c` 和 `/mnt/d` 性能警告

Windows 盘通过 9P 挂载进 WSL。对大量随机读取的模型流式推理来说，性能远不如 WSL ext4 内部文件。

推荐：

```text
模型：放在 WSL ext4 内，如 ~/MyProjects/model-learning/models
导出结果：可以少量复制到 /mnt/c 或 /mnt/d
```

不推荐：

```text
把 54 GiB Qwen 模型放在 /mnt/c/... 然后流式随机读取
```

## 5. 性能记录

### 5.1 SD1.5 冒烟

命令：

```bash
python sd15_model.py \
  --steps 1 \
  --threads 14 \
  --output .tmp-doc-sd-smoke.png
```

结果：

| 阶段 | 时间 |
|---|---:|
| 整体命令 | 约 14.4 s |
| 模型加载 | 2.8 s |
| 1 步生成 | 8.9 s |

1 步不代表画质，只验证环境和数据流。

### 5.2 Qwen-Image 流式

历史量级参考：

```text
512×512：约 60 s / step
```

该数字来自同类 WSL2/i5-14400 环境，实际会受以下因素影响：

- 文件是否已进入 page cache；
- 分辨率；
- prompt 长度；
- 是否启用 CFG；
- 后台负载；
- 磁盘读取模式；
- 库版本。

## 6. CPU 线程微基准

在当前环境中，PyTorch 默认只使用 8 个 intra-op 线程，而机器有 16 个逻辑线程。用 2048×2048 矩阵乘法测试：

| 线程数 | 单次耗时 | 有效吞吐 |
|---:|---:|---:|
| 8 | 0.037s | 0.47 TFLOPS |
| 10 | 0.030s | 0.57 TFLOPS |
| 12 | 0.027s | 0.63 TFLOPS |
| 14 | 0.029s | 0.59 TFLOPS |
| 16 | 0.029s | 0.58 TFLOPS |

结论：`12 threads` 是当前环境下较好的起点。`qwen-image-2512.py` 已提供 `--threads` 参数，默认改为 12。

补充一次 512×512、1 步、无 CFG 的端到端冒烟对比：

| 线程数 | 去噪步耗时 |
|---:|---:|
| 12 | 62.1s |
| 8 | 63.7s |

实际端到端收益约 2.5%，远小于 GEMM 微基准差异。这说明 Qwen-Image 的瓶颈不只在矩阵乘法线程数，还包括权重 I/O、attention、内存带宽和调度开销。

这只能改善 CPU 线程调度和算子并行，不能改变 Qwen-Image 本身的计算量。若启用了负面提示词，batched true CFG 仍会让每步计算量接近翻倍。

## 7. 为什么 Qwen 流式可行但慢？

流式加载用 I/O 换内存：

```text
内存需求：降低
磁盘 I/O：增加
计算次数：不减少
```

CPU 推理的瓶颈可能来自：

1. 权重从磁盘读入内存；
2. bf16/fp32 转换；
3. 大量矩阵乘法；
4. attention 计算和中间激活；
5. Python 调度和线程同步。

预取只能让磁盘读取与计算重叠，不能让 CPU 本身的计算能力变强。

## 8. 如果要提速，优先级是什么？

| 优先级 | 方案 | 预期效果 | 是否保持原图 |
|---|---|---|---|
| 1 | 使用大显存/高性能 GPU | 最大提升，可能是数量级 | bf16 语义下接近无损；硬件浮点顺序可能有微小差异 |
| 2 | TensorRT/ONNX/专用 DiT 推理引擎 | 提高算子融合和 attention 效率 | 取决于精度与 kernel，需要对比验证 |
| 3 | FP8/int8/int4/GGUF | 减少 I/O、内存和计算 | 通常改变数值和画质 |
| 4 | 更小/蒸馏/Lightning 模型 | 可能比优化大模型更有效 | 换模型，输出不同 |
| 5 | prompt embedding 缓存 | 同一 prompt 多图时省文本编码 | 无损 |
| 6 | CPU 权重前缀缓存 | 减少约 6GiB 权重的重复 I/O/转换 | 无损 |
| 7 | batched true CFG | 减少权重读取次数，但增加单次 batch 计算 | 与两次独立 forward 的浮点组织可能不同，需固定 seed 验证 |
| 8 | 部分 CFG | 减少后半段 CFG 计算量 | 改变输出，非无损 |
| 9 | 更快 NVMe/更大 RAM | 改善 I/O 和缓存命中率 | 无损 |

对当前 19 GiB CPU 环境而言，流式 Qwen-Image 适合作为学习、验证和优化研究对象。若目标是 1024 级别实用生成，建议把本机作为基线和控制系统，把重计算放到消费级 NVIDIA GPU 或云端 GPU 上。

## 8.1 消费级加速研究路线

### 阶段 1：建立无损基线

在本机固定 seed、尺寸、prompt、负面提示词和 50 步，分别记录：

```text
512×512 / 1 step
1024×1024 / 1 step
```

可用同一组 prompt 先跑 1 步建立基线：

```bash
python qwen-image-2512.py \
  --model ./models/Qwen-Image-2512 \
  --prompt-file ./prompt.txt \
  --negative-prompt-file ./negative_prompt.txt \
  --width 1024 --height 1024 \
  --steps 1 \
  --threads 12 \
  --cpu-cache-gib 6 \
  --output qwen-1024-1step.png
```

记录总耗时、每步耗时、`load_seconds`、RSS 峰值、CPU 占用和磁盘读取量。先不要直接跑 50 步 1024；1 步足以推算量级。

### 阶段 2：本机无损优化

- `--threads 12`；
- `--cpu-cache-gib 6`；
- prompt embedding 缓存；
- 关闭后台任务，避免 swap；
- 模型放在 WSL ext4/NVMe 上，不放 `/mnt/c`；
- 对比 `--cpu-cache-gib 4/6/8`。

这些优化不改变输出，但主要减少 I/O 和启动成本，无法改变 CPU 每秒可完成的浮点运算量。

### 阶段 3：引入消费级 NVIDIA GPU

优先评估：

- 24GB 显卡：bf16 权重不能全驻留，可用系统 RAM + 分层流式/组卸载；FP8/GGUF 可驻留但需画质验证；
- 32GB 显卡：bf16 transformer 仍略超显存，可结合少量卸载；
- 更高端/大显存卡：越接近全驻留，效率越稳定。

同时调研这些开源方向：

- `stable-diffusion.cpp`：C/C++ 实现，支持 Qwen Image 和 GGUF，偏量化/低资源路线；
- `Qwen-Image-TensorRT`：把 Qwen-Image DiT 转 TensorRT，目标是 NVIDIA GPU 高吞吐；
- `KsanaDiT`：高性能 DiT 推理框架，包含 FP8、Torch Compile、Flash/Sage attention、多 GPU 和缓存策略；
- ComfyUI 生态的 GGUF/SDNQ 权重与加载器。

研究方法不是直接替换，而是固定同一 prompt/seed/步数，记录速度、显存、RSS 和图像差异，再决定是否接受其精度变化。

### 阶段 4：质量/速度折中实验

在无损路线无法满足目标时再做：

- `--cfg-steps 0/10/20/30`；
- FP8/int8/GGUF Q8/Q4；
- Lightning/蒸馏模型；
- 1024 生成 + 高质量超分。

每一项都必须明确标记为“会改变输出”，不能和无损优化混在同一个基线里。

## 9. 建议的实验流程

```text
1. SD1.5 1 步冒烟       → 确认依赖和模型可用
2. SD1.5 20 步生成      → 建立质量直觉
3. 阅读 Qwen model_index → 理解组件和分片
4. Qwen 2 步流式冒烟    → 验证流式执行器
5. Qwen 8 步低分辨率    → 观察画质变化
6. 同 seed 修改 prompt  → 理解文本条件影响
7. 记录每步耗时和内存    → 建立自己的性能基线
```

## 11. 结论

- **SD1.5**：当前机器完全适合学习，CPU 生成可接受。
- **Qwen-Image 非流式**：本机内存不够，必须换机器。
- **Qwen-Image 流式**：当前机器可以做实验，但速度慢；价值在于深入理解 safetensors、meta model、forward hook、预取和推理内存管理。
