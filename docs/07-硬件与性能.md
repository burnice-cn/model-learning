# 07. 硬件与性能

> 记录日期：2026-09-16  
> 环境：Windows + WSL2 Ubuntu 24.04.3，项目目录位于 WSL ext4 文件系统内。

## 1. 系统概览

| 项目 | 当前值 |
|---|---|
| 操作系统 | Ubuntu 24.04.3 LTS |
| 内核 | 6.18.33.2-microsoft-standard-WSL2 |
| 主机环境 | Windows + WSL2 |
| CPU | Intel Core i5-14400 |
| 逻辑线程 | 16 |
| WSL 内存上限 | 19 GiB |
| Swap | 8 GiB |
| 可用 NVIDIA GPU | 无 |

WSL2 不是裸金属 Linux：

- `/` 是虚拟磁盘；
- I/O 行为与真实 Linux 磁盘不完全相同；
- 内存实际来自 Windows 宿主机；
- 如果进入 swap，推理速度可能极差。

| 项目 | 值 |

| 逻辑 CPU | 16 |
| 物理核心视角 | 8 核 16 线程 |
| L1d | 384 KiB |

### 指令集

| 指令集 | 支持 | 意义 |
|---|---|---|
| AVX2 | 支持 | 256 位向量计算 |
| FMA | 支持 | 融合乘加，有助矩阵乘法 |
| AVX-VNNI | 支持 | int8 点积加速潜力 |
| SSE4.2 | 支持 | 基础兼容 |
| AVX-512 | 不支持 | 不应写依赖 AVX-512 的优化 |
| AMX | 不支持 | 不应依赖 Intel 矩阵扩展 |

结论：这台 CPU 有基础的 AVX2/FMA 推理能力，也有 int8 优化潜力，但没有 AVX-512/AMX，不能期望达到高端推理服务器的吞吐。

## 4. 存储

### 4.1 WSL 与 Windows 磁盘

当前观察：

```text
/         可用显示约 775 GiB
C:        可用约 33 GiB
D:        可用约 165 GiB
```

`df -h /` 显示的是 WSL 虚拟文件系统的可用空间，不能简单等同于 Windows 宿主盘的长期可用空间。WSL 的 VHDX 实际由 Windows 物理盘支撑，继续写入最终仍受宿主盘限制。

### 4.2 模型占用

```text
models/stable-diffusion-v1-5  约 2.0 GB
models/Qwen-Image-2512        约 54 GB
```

### 4.3 `/mnt/c` 和 `/mnt/d` 性能警告

Windows 盘通过 9P 挂载进 WSL。对大量随机读取的模型流式推理来说，性能远不如 WSL ext4 内部文件。

推荐：

```text
模型：放在 WSL ext4 内，如 ~/MyProjects/model-learning/models
导出结果：可以少量复制到 /mnt/c 或 /mnt/d
```

不推荐：

```text
把 54 GiB Qwen 模型放在 /mnt/c/... 然后流式随机读取
```

## 5. 性能记录

### 5.1 SD1.5 冒烟

命令：

```bash
python sd15_model.py \
  --steps 1 \
  --threads 14 \
  --output .tmp-doc-sd-smoke.png
```

结果：

| 阶段 | 时间 |
|---|---:|
| 整体命令 | 约 14.4 s |
| 模型加载 | 2.8 s |
| 1 步生成 | 8.9 s |

1 步不代表画质，只验证环境和数据流。

### 5.2 Qwen-Image 流式

历史量级参考：

```text
512×512：约 60 s / step
```

该数字来自同类 WSL2/i5-14400 环境，实际会受以下因素影响：

- 文件是否已进入 page cache；
- 分辨率；
- prompt 长度；
- 是否启用 CFG；
- 后台负载；
- 磁盘读取模式；
- 库版本。

## 6. CPU 线程微基准

在当前环境中，PyTorch 默认只使用 8 个 intra-op 线程，而机器有 16 个逻辑线程。用 2048×2048 矩阵乘法测试：

| 线程数 | 单次耗时 | 有效吞吐 |
|---:|---:|---:|
| 8 | 0.037s | 0.47 TFLOPS |
| 10 | 0.030s | 0.57 TFLOPS |
| 12 | 0.027s | 0.63 TFLOPS |
| 14 | 0.029s | 0.59 TFLOPS |
| 16 | 0.029s | 0.58 TFLOPS |

结论：`12 threads` 是当前环境下较好的起点。`qwen-image-2512.py` 已提供 `--threads` 参数，默认改为 12。

补充一次 512×512、1 步、无 CFG 的端到端冒烟对比：

| 线程数 | 去噪步耗时 |
|---:|---:|
| 12 | 62.1s |
| 8 | 63.7s |

实际端到端收益约 2.5%，远小于 GEMM 微基准差异。这说明 Qwen-Image 的瓶颈不只在矩阵乘法线程数，还包括权重 I/O、attention、内存带宽和调度开销。

这只能改善 CPU 线程调度和算子并行，不能改变 Qwen-Image 本身的计算量。若启用了负面提示词，batched true CFG 仍会让每步计算量接近翻倍。

## 7. 为什么 Qwen 流式可行但慢？

流式加载用 I/O 换内存：

```text
内存需求：降低
磁盘 I/O：增加
计算次数：不减少
```

CPU 推理的瓶颈可能来自：

1. 权重从磁盘读入内存；
2. bf16/fp32 转换；
3. 大量矩阵乘法；
4. attention 计算和中间激活；
5. Python 调度和线程同步。

预取只能让磁盘读取与计算重叠，不能让 CPU 本身的计算能力变强。

## 8. 如果要提速，优先级是什么？

| 优先级 | 方案 | 预期效果 |
|---|---|---|
| 1 | 使用大显存 GPU | 最大提升 |
| 2 | 使用更小/蒸馏模型 | 可能比优化大模型更有效 |
| 3 | int8/int4 量化 | 减少内存和 I/O，需要验证兼容性与质量 |
| 4 | 缓存 prompt embedding | 同一 prompt 多图时可省文本编码 |
| 5 | batched true CFG | 减少权重读取次数，但增加单次 batch 显存 |
| 6 | 更快 NVMe/更大 RAM | 改善 I/O 和缓存命中率 |

对当前 19 GiB CPU 环境而言，流式 Qwen-Image 更适合作为学习与验证工具，而不是实用生产路径。

## 9. 建议的实验流程

```text
1. SD1.5 1 步冒烟       → 确认依赖和模型可用
2. SD1.5 20 步生成      → 建立质量直觉
3. 阅读 Qwen model_index → 理解组件和分片
4. Qwen 2 步流式冒烟    → 验证流式执行器
5. Qwen 8 步低分辨率    → 观察画质变化
6. 同 seed 修改 prompt  → 理解文本条件影响
7. 记录每步耗时和内存    → 建立自己的性能基线
```

## 11. 结论

- **SD1.5**：当前机器完全适合学习，CPU 生成可接受。
- **Qwen-Image 非流式**：本机内存不够，必须换机器。
- **Qwen-Image 流式**：当前机器可以做实验，但速度慢；价值在于深入理解 safetensors、meta model、forward hook、预取和推理内存管理。
